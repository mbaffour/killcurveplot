# Audit fixes — 2026-09

This document tracks disposition of the killcurveplot findings (KC-1…KC-11) from
the 2026-09 read-only audit
(`killcurveplot-cfu-plot-studio.md`, section 2). All eleven were fixed on branch
`claude/audit-2026-09`; none were deferred or declined. See `CHANGELOG.md` (v2.9.0)
for the user-facing summary and `docs/METRICS_REFERENCE.md` for the metrics-level
detail.

Both test suites were run before every commit. `tests/test_v28.R` grew from 52 to
101 checks and passes in full. `tests/test_metrics_parity.R` is discussed under
KC-5 below — its reference-free checks (rolling_slope parity, infection-metric
self-consistency, hand-computed spot checks) pass unconditionally; its
reference-*comparison* checks currently cannot run in this environment because the
sibling `lysis-curve-app` clone has moved on to a structurally different v3.0 (see
KC-5).

## KC-1 (P0) — Fixed

`prepare_plot_data()` (`Lysis_Curve_App_v28.R`) no longer coerces `sd_value` /
`sem_value` / `ci95_value` to `0` when a time point has exactly one replicate.
`sd()` of one value is genuinely `NA`; that `NA` now survives into the plot's
error-bar layer (which drops the row rather than drawing a zero-height bar),
the Summary Statistics CSV, and both report formats. `README.md`'s
troubleshooting note ("the standard deviation is zero") is corrected to say
it is undefined. Commit `413cc7b`; tests added in `tests/test_v28.R`
("KC-1: …", 7 checks).

**Deviation from the literal audit text:** none. Implemented exactly as
proposed.

## KC-2 (P1) — Fixed

`compute_one_curve_metrics()` (formerly the body of `compute_curve_metrics()`)
now treats a non-positive OD reading as missing for the log-scale μmax
regression: any rolling window that touches one is blanked to `NA`, rather
than the old `log(pmax(od_vec, 1e-9))` clamp that put an artificial ~20-log-
unit slope into the window and inflated μmax. A new `n_nonpositive_od`
per-sample column and a sidebar warning surface the count so an affected
sample is visible rather than silently plausible. Commit `eeee802`; tests
hand-verify the exact ln(2)/10 slope against a deliberately-corrupted first
reading, and directly demonstrate the old clamp would have produced a much
larger (wrong) value.

**Deviation:** the audit's proposed fix also asked to "surface a count of
non-positive readings in the data-summary box and the report provenance
section." I surfaced it as (a) a `n_nonpositive_od` column in every Curve
Metrics export (CSV, and both reports, since those tables are generic) and
(b) a dedicated sidebar warning next to the metrics controls, rather than
threading a new row into the HTML/PDF report's fixed-shape provenance table
(`build_html_report`/`build_pdf_report`), which would have required
restructuring both report builders' hard-coded provenance-row layout for
comparatively little additional benefit given (a) already ships in every
export that contains the metrics. Noted here as a scope trade-off, not an
omission.

## KC-3 (P2) — Fixed (additive, off by default)

Added `moving_average()` (a simple, documented centered moving average) and
a `peak_smooth_window` parameter to the metrics engine (default `1` = off,
so existing exports are bit-for-bit unchanged unless a user opts in). When
raised, only the *peak's index* is located on the smoothed curve; every
reported OD value still comes from the raw data at that index. A new
sidebar control ("Peak-detection smoothing window") and documentation in
`docs/METRICS_REFERENCE.md` explain why this matters (all
lysis-onset-anchored metrics inherit peak-detection instability) and that
the default is off. Commit `7c297b7`; test constructs two deterministic
"noisy" curve variants whose raw peak lands at different time points and
shows both stabilize to the true peak once smoothing is enabled.

**Deviation:** the audit offered two options — "optional curve smoothing
before peak detection, or take the peak as the maximum of a smoothed/
rolling-median curve while reporting ODs from the raw data." I implemented
the second (peak located on smoothed data, values always raw), which is the
narrower, lower-risk change: it touches only `which.max()`'s input, not the
lysis-decline threshold detection or the AUC/mu_max calculations, so it
cannot change any metric when left at its default. Savitzky-Golay was not
implemented — a simple centered moving average was judged sufficient and
matches the audit's own suggested alternative ("e.g. a simple moving average
or Savitzky-Golay").

## KC-4 (P2) — Fixed (additive)

Factored the per-curve metrics engine out into `compute_one_curve_metrics()`
(a pure function of one `t_vec`/`od_vec` curve — refactor verified
byte-for-byte via the full existing test suite passing unchanged). Added
`prepare_replicate_data()` (the un-averaged counterpart of
`prepare_plot_data()`) and `compute_replicate_metrics()`, which runs the
identical engine once per individual replicate curve and reports
`<metric>_mean`/`<metric>_sd` across replicates per sample. Wired to a new
"Per-Replicate Metrics, mean ± SD (CSV)" download, additive alongside the
existing "Curve Metrics (CSV)". Commit `b2f7041`; tests include a
hand-computable case proving the per-replicate mean of `max_od` is *not*
equal to `max_od` of the mean curve (nonlinear metric), and a case proving
an `NA` metric on one replicate is excluded from, not zeroed into, the
mean/SD.

**Deviation:** for long-format files with no explicit replicate-ID column,
replicate identity is inferred from row order within each `(sample, time)`
group — documented in `docs/METRICS_REFERENCE.md` and the sidebar help text
as an assumption, not hidden. This was the only viable option without
requiring a new required column in the CSV format; adding a first-class
replicate-ID column to the long-format contract was judged out of scope
(it would change the documented data format itself, not just the metrics
engine). The per-replicate summary was **not** added to the HTML/PDF
reports (kept to the CSV export) — a reasonable scope boundary given the
CSV already satisfies "report... alongside the mean-curve metric," and the
report builders would need a second, differently-shaped wide table added to
their hard-coded layout.

## KC-5 (P2) — Fixed

`tests/test_metrics_parity.R` restructured: reference-free checks
(`rolling_slope` vs `zoo::rollapply`, infection-metric self-consistency and
absence checks, hand-computed spot checks) now run unconditionally instead
of being gated behind the reference-clone check. When the reference is
unavailable — either missing, or present but its
`calculate_growth_metrics()` signature has drifted from what this suite's
`grab()`-based line-slicing extraction expects — that is now a visible
**failure by default** (previously `quit(status = 0)`), naming the cause;
`ALLOW_SKIP=1` downgrades it to a clearly-printed skip instead. Commit
`81f1722`.

**Important finding surfaced by this fix, not by the original audit:** the
sibling `lysis-curve-app` clone at `../lysis-curve-app` (owned by another
agent/session, out of scope for this repo to edit) has moved on from the
`v26.03.13`/v2.9-era shape this suite was written against to a **v3.0
rewrite** — it now calls a `curve_noise_sd()` helper and a
`first_prominent_peak_idx()` peak-anchoring function that this suite's
`grab()` extraction (by design, line-slicing between two regex anchors, as
the original audit already flagged as brittle) does not pull in. In this
repo's current environment, running `Rscript tests/test_metrics_parity.R`
therefore **fails by default** with a clear
`"reference extraction/call failed: could not find function \"curve_noise_sd\""`
message — this is expected and correctly attributed to the sibling's
independent evolution, not a regression introduced here. `ALLOW_SKIP=1`
was used during development to confirm the rest of the suite (20 checks)
is otherwise green. See "Relationship to sibling repos" below.

**Deviation:** I went further than the literal ask (which was only about
the missing-file case) because, once implemented, the same code path
naturally needed to cover "present but incompatible" too — the audit's own
text anticipated this ("an edit to the reference app silently changes what
is compared"), and leaving that case unhandled would have reintroduced a
silent-pass risk of a different shape. I did **not** attempt to update the
`grab()` extraction to pull in the reference's new v3.0 helper functions
(`curve_noise_sd`, `first_prominent_peak_idx`, `LYSIS_SUSTAIN_PTS`) — that
would mean chasing a moving target I don't own, is explicitly out of scope
("killcurveplot's relationship to them is informational only... don't sync
code"), and the port-fidelity value of doing so is questionable now that
the reference has independently adopted a different peak-anchoring
strategy (first-prominent-peak vs. this repo's global-max) that this repo
was never asked to match.

## KC-6 (P2) — Fixed

`show_error_caption` now defaults to `TRUE` in both the initial UI widget
and the "Clear imported settings" reset (previously `FALSE` in both). Since
`error_type` already defaults to `"sem"`, a first-run figure now always
states the error measure and n. Commit `231f2f1`.

**Deviation:** the audit offered two alternatives ("default
`show_error_caption = TRUE`, or default `error_type` to `\"sd\"`"). I chose
the caption default, which is strictly additive (never changes what error
type is plotted, only whether it's labelled) — changing the default error
*type* from SEM to SD would silently change every default figure's error
bar width for existing users, which is a larger, unrequested behavior
change.

## KC-7 (P2) — Fixed (additive, off by default)

Added a "Subtract blank/media OD" sidebar field (`blank_od`, default `0`).
Applied once, at the end of `prepare_plot_data()` and
`prepare_replicate_data()` — mathematically equivalent to subtracting the
same constant from every raw reading first (a constant offset commutes with
averaging; SD is shift-invariant either way). Recorded in the report
provenance table; included in save/load settings and the Clear-settings
reset for consistency with the other analysis-control inputs
(`metrics_smooth_window`, `metrics_peak_smooth_window`). Documented in
README.md. Commit `e207fa6`.

**Deviation:** implemented as a single global constant rather than a
per-sample or per-well blank, which the audit's phrasing ("optional
blank/media subtraction if straightforward to add") allowed for — a single
global value is the straightforward case; per-sample blanks would need a
new UI concept (one blank value per selected sample, or a blank "sample" to
subtract) that is a materially larger feature than what was authorized here.

## Relationship to sibling repos (informational only)

Per instructions, `cfu-plot-studio`, `lysis-curve-app`, and
`N4-Lysis-paper-codes` were not edited from this session — they are owned by
other agents/sessions. Two things worth recording here because they surfaced
directly from work on *this* repo's tests:

- **`lysis-curve-app` has evolved past what `tests/test_metrics_parity.R`
  expects.** At audit time it was effectively v2.9-era
  (`Lysis Curve Ap 26.03.13.R`, the file this suite still points at by
  default). It is now a v3.0 "Complete phenotyping platform"
  (10,075 lines, up from a much smaller original) with new internals
  (`curve_noise_sd()`, `first_prominent_peak_idx()`, `LYSIS_SUSTAIN_PTS`,
  a `calculate_growth_metrics(plot_data, smooth_window, extinction_threshold)`
  signature) that this suite's brittle `grab()`-based extraction cannot pull
  in. See KC-5 above for how this repo now handles that (fail loudly by
  default, `ALLOW_SKIP=1` to skip visibly) rather than silently ignoring it.
  This is purely a test-infrastructure observation; it says nothing about
  either app's correctness.
- **Two of `lysis-curve-app`'s v3.0 commit messages describe fixes that
  parallel two of this repo's own findings** — "Exclude non-positive OD from
  the log windows instead of clamping it" (parallel to KC-2 here) and a
  peak-anchoring change (related in spirit to KC-3 here, though a different
  technique — first-prominent-peak vs. this repo's smoothed-global-max).
  This is coincidental convergence on the same class of bug in two
  independently-audited codebases sharing a lineage, not a dependency
  between the fixes — no code was compared or copied in either direction for
  this task.
